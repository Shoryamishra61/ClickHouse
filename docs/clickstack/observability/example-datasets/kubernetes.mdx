Collect logs and metrics from your Kubernetes cluster and send them to **ClickHouse Observability** for visualization and analysis. Monitor your existing pods, nodes, and containers.

## Prerequisites {#prerequisites}

This guide requires you to have:

- A running **Kubernetes cluster** with workloads to monitor.
- A **ClickHouse Observability service** and its managed telemetry endpoint and API key.
- **[Helm](https://helm.sh/)** v3+
- **`kubectl`**, configured to interact with your cluster, with permission to create namespaces, Secrets, ConfigMaps, and cluster roles.
- Outbound HTTPS access from the collector pods to your managed telemetry endpoint on the port shown in **Managed Telemetry**.

## Deployment {#deployment}

Deploy OpenTelemetry Collectors in your Kubernetes cluster to collect logs and metrics and forward them to your managed telemetry endpoint. ClickHouse Observability manages data ingestion, storage, and the UI, so you do not need to deploy ClickHouse, HyperDX, or MongoDB in your cluster.

<Steps>
<Step title="Copy your connection details" id="copy-connection-details">

Open your ClickHouse Observability service and go to **Team Settings → Managed Telemetry**. Under **OpenTelemetry Collector**, select the **URL** tab and copy the OTLP HTTP endpoint and API key. Select **Reveal key** to view the full values.

Use these connection details to configure the Kubernetes collectors in the following steps.

<Image img="/images/clickstack/getting-started/observability-managed-telemetry.png" alt="Managed Telemetry showing the OTLP endpoint and API key connection details" size="lg"/>
</Step>
<Step title="Store your connection details" id="create-api-key-kubernetes-secret">

Store the managed telemetry API key in a Kubernetes Secret and the OTLP HTTP endpoint in a ConfigMap. Create both in the namespace where you will install the collectors. The examples below use a dedicated `otel-collectors` namespace.

```shell
kubectl create namespace otel-collectors

kubectl create secret generic hyperdx-secret \
  --namespace otel-collectors \
  --from-literal=HYPERDX_API_KEY='<api-key>'

kubectl create configmap otel-config-vars \
  --namespace otel-collectors \
  --from-literal=YOUR_OTEL_COLLECTOR_ENDPOINT='<managed-otlp-http-endpoint>'
```

If the namespace already exists, skip the first command. Replace the placeholders with the values from **Managed Telemetry**, keeping the endpoint's HTTPS scheme and port.
</Step>
<Step title="Add the OpenTelemetry Helm repo" id="add-otel-helm-repo">

Use the official OpenTelemetry Helm chart to deploy collectors that send logs and metrics to your managed telemetry endpoint.

Add the chart repository and refresh its index:

```shell
helm repo add open-telemetry https://open-telemetry.github.io/opentelemetry-helm-charts
helm repo update open-telemetry
```
</Step>
<Step title="Deploy Kubernetes collector components" id="deploy-kubernetes-collector-components">

To collect logs and metrics from both the cluster itself and each node, we'll need to deploy two separate OpenTelemetry collectors, each with its own Helm values file. The two files provided - `k8s_deployment.yaml` and `k8s_daemonset.yaml`  - work together to collect comprehensive telemetry data from your Kubernetes cluster.

- `k8s_deployment.yaml` deploys a **single OpenTelemetry Collector instance** responsible for collecting **cluster-wide events and metadata**. It gathers Kubernetes events, cluster metrics, and enriches telemetry data with pod labels and annotations. This collector runs as a standalone deployment with a single replica to avoid duplicate data.

- `k8s_daemonset.yaml` deploys a **DaemonSet-based collector** that runs on every node in your cluster. It collects **node-level and pod-level metrics**, as well as container logs, using components like `kubeletstats`, `hostmetrics`, and Kubernetes attribute processors. These collectors enrich logs with metadata and send them to your managed telemetry endpoint using the OTLP HTTP exporter.

Both collectors export directly to ClickHouse Observability. On a single-node cluster, this creates two collector pods. Collecting application traces additionally requires application instrumentation.

The commands below download each Helm values file before installing its collector. Expand the configuration below each command to inspect its contents. These examples use Helm chart `0.175.0` with Collector `0.161.0`.

First, install the collector as a Deployment:

```shell
curl -fSL -o k8s_deployment.yaml \
  https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_deployment.yaml

helm install --namespace otel-collectors k8s-otel-deployment open-telemetry/opentelemetry-collector \
  --version 0.175.0 -f k8s_deployment.yaml
```

<Accordion title="k8s_deployment.yaml">
```yaml
# k8s_deployment.yaml
mode: deployment

image:
  repository: otel/opentelemetry-collector-contrib
  tag: 0.161.0
 
# We only want one of these collectors - any more and we'd produce duplicate data
replicaCount: 1
 
presets:
  kubernetesAttributes:
    enabled: true
    # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
    # The label's exact name will be the key.
    extractAllPodLabels: true
    # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
    # The annotation's exact name will be the key.
    extractAllPodAnnotations: true
  # Configures the collector to collect Kubernetes events.
  # Adds the k8sobject receiver to the logs pipeline and collects Kubernetes events by default.
  # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-objects-receiver
  kubernetesEvents:
    enabled: true
  # Configures the Kubernetes Cluster Receiver to collect cluster-level metrics.
  # Adds the k8s_cluster receiver to the metrics pipeline and adds the necessary rules to ClusterRole.
  # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-cluster-receiver
  clusterMetrics:
    enabled: true

extraEnvs:
  - name: HYPERDX_API_KEY
    valueFrom:
      secretKeyRef:
        name: hyperdx-secret
        key: HYPERDX_API_KEY
  - name: YOUR_OTEL_COLLECTOR_ENDPOINT
    valueFrom:
      configMapKeyRef:
        name: otel-config-vars
        key: YOUR_OTEL_COLLECTOR_ENDPOINT
 
config:
  exporters:
    otlp_http:
      endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
      compression: gzip
      headers:
        authorization: "Bearer ${env:HYPERDX_API_KEY}"
  service:
    pipelines:
      logs:
        exporters:
          - otlp_http
      metrics:
        exporters:
          - otlp_http

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 512Mi
```
</Accordion>

Next, deploy the collector as a DaemonSet for node and pod-level metrics and logs:

```shell
curl -fSL -o k8s_daemonset.yaml \
  https://raw.githubusercontent.com/ClickHouse/ClickHouse/master/docs/clickstack/observability/example-datasets/_snippets/k8s_daemonset.yaml

helm install --namespace otel-collectors k8s-otel-daemonset open-telemetry/opentelemetry-collector \
  --version 0.175.0 -f k8s_daemonset.yaml
```

<Accordion title="k8s_daemonset.yaml">
```yaml
# k8s_daemonset.yaml
mode: daemonset

image:
  repository: otel/opentelemetry-collector-contrib
  tag: 0.161.0
   
# Required to use the kubeletstats cpu/memory utilization metrics
clusterRole:
  create: true
  rules:
    - apiGroups:
        - ''
      resources:
        - nodes/proxy
      verbs:
        - get
 
presets:
  logsCollection:
    enabled: true
  hostMetrics:
    enabled: true
  # Configures the Kubernetes Processor to add Kubernetes metadata.
  # Adds the k8sattributes processor to all the pipelines and adds the necessary rules to ClusterRole.
  # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubernetes-attributes-processor
  kubernetesAttributes:
    enabled: true
    # When enabled, the processor will extract all labels for an associated pod and add them as resource attributes.
    # The label's exact name will be the key.
    extractAllPodLabels: true
    # When enabled, the processor will extract all annotations for an associated pod and add them as resource attributes.
    # The annotation's exact name will be the key.
    extractAllPodAnnotations: true
  # Configures the collector to collect node, pod, and container metrics from the kubelet API.
  # Adds the kubeletstats receiver to the metrics pipeline and adds the necessary rules to ClusterRole.
  # More Info: https://opentelemetry.io/docs/kubernetes/collector/components/#kubeletstats-receiver
  kubeletMetrics:
    enabled: true

extraEnvs:
  - name: HYPERDX_API_KEY
    valueFrom:
      secretKeyRef:
        name: hyperdx-secret
        key: HYPERDX_API_KEY
  - name: YOUR_OTEL_COLLECTOR_ENDPOINT
    valueFrom:
      configMapKeyRef:
        name: otel-config-vars
        key: YOUR_OTEL_COLLECTOR_ENDPOINT

config:
  receivers:
    kubeletstats:
      insecure_skip_verify: true
  exporters:
    otlp_http:
      endpoint: "${env:YOUR_OTEL_COLLECTOR_ENDPOINT}"
      compression: gzip
      headers:
        authorization: "Bearer ${env:HYPERDX_API_KEY}"
 
  service:
    pipelines:
      logs:
        exporters:
          - otlp_http
      metrics:
        exporters:
          - otlp_http

resources:
  requests:
    cpu: 100m
    memory: 128Mi
  limits:
    memory: 512Mi
```
</Accordion>

The DaemonSet example sets `insecure_skip_verify: true` for the local kubelet connection because local clusters can use certificates that do not cover the node address. For production, configure a trusted kubelet certificate and enable certificate verification. This setting does not affect TLS verification for the managed telemetry endpoint.

Check that the collectors are ready:

```shell
kubectl get pods --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector
kubectl logs --namespace otel-collectors -l app.kubernetes.io/name=opentelemetry-collector --prefix --tail=50
```

Look for authentication, export, or scrape errors in the logs. A running pod alone does not confirm that telemetry has been delivered.
</Step>
<Step title="Verify logs and metrics in ClickHouse Observability" id="verify-kubernetes-data">

Open your ClickHouse Observability service. In [Search](/clickstack/observability/features/search), select the **Logs** source and a time range that includes when the collectors were running. Look for a log message from one of your workloads and inspect its Kubernetes resource attributes, such as `k8s.namespace.name` and `k8s.pod.name`.

The example below shows logs from a local Kubernetes cluster, including a `sample-logs` workload emitting `Kubernetes documentation test` messages. Your service names and log messages will depend on your workloads.

<Image img="/images/clickstack/getting-started/observability-kubernetes-logs.png" alt="Search showing sample workload and Kubernetes system logs arriving from a local cluster" size="lg"/>

In **Chart Explorer**, select **Time Series** and the **Metrics** source. Choose **Average** of `k8s.pod.memory.usage`, group by `ResourceAttributes['k8s.pod.name']`, and leave **Delta** unchecked. Select a time range that includes when the collectors were running, then select **Run** to compare memory usage across pods. If the chart has gaps, choose a time granularity at least as large as the collection interval.

<Image img="/images/clickstack/getting-started/observability-kubernetes-metrics.png" alt="Chart Explorer showing average Kubernetes pod memory usage grouped by pod name" size="lg"/>

To explore the prebuilt Kubernetes dashboard, open **Dashboards** in the sidebar and select **Kubernetes** under **Preset Dashboards**. Select the **Logs** and **Metrics** sources and a time range that includes when the collectors were running.

Use the **Pods**, **Nodes**, and **Namespaces** tabs to explore your cluster. You can narrow the view using the pod, deployment, node, namespace, and cluster filters.

<Image img="/images/clickstack/getting-started/observability-kubernetes-dashboard.png" alt="Fully managed Kubernetes dashboard showing pod CPU and memory usage, pod status, and Kubernetes warning events" size="lg"/>


</Step>
</Steps>
